## Authority and boundaries

- The additive SQLite schema is `SCHEMA` in `apps/api/src/openforge_api/task_annotations.py`: viewer email, exact Profile ID and source occurrence identity form the primary key. The Profile foreign key cascades annotations only if the Profile is deleted by its existing authority. No financial table, calculation or source-task lifecycle is changed.
- `GET` and `PATCH /fund-manager/tasks/annotations` require a server-validated Fund Manager session, a currently authorised active Profile and the matching runtime flag. The isolated flag works only in candidate/test storage; `OPENFORGE_TASK_ANNOTATIONS_NORMAL_ENABLED` works only for normal-owner SQLite and defaults false. Neither flag grants access to another runtime. Ordinary API startup never creates the annotation schema.
- PATCH accepts 1–32 changes, rejects duplicate identities and stale versions, and uses conditional SQL writes in one transaction. An identical retry returns its existing version. A missing/changed source cannot be newly tracked; an existing unavailable item may be untracked. Source status remains `active`, `resolved`, `changed` or `unavailable`, without altering the source, notification read state or financial records.
- Full protected SQLite backups include annotations. The ordinary Profile portable export uses an explicit sheet allowlist and excludes annotations; viewer-owned portability requires a separate contract.
- This activation is local SQLite only. PostgreSQL/hosted use requires separate review.
